# Architecture

`restaurant-manager-api` is a Bun-native HTTP API for restaurant management. It is built as a
layered TypeScript service: Hono handles HTTP routing, Zod OpenAPI defines and validates the
contract, Drizzle ORM owns persistence, and Better Auth provides authentication/authorization.
Everything runs on the Bun runtime, and Bun is also the package manager, test runner, and
script runner.

> **Current state:** the repository is a scaffold. `src/index.ts` is empty, so no dependency is
> imported yet. This document records the declared stack in `package.json`, the resolved versions
> from `bun.lock`, and the role each package is expected to play as the codebase is built out.

## High-level layers

```
Client
  │  HTTP (JSON)
  ▼
Hono app  ──  @hono/zod-openapi route definitions (request/response schemas)
  │           @hono/swagger-ui  →  /docs (OpenAPI UI)
  │           http-status-codes →  consistent status constants
  ▼
Middleware  ──  Better Auth session middleware (@better-auth/drizzle-adapter)
  ▼
Domain / services  ──  slugify, nanoid (identifiers, slugs)
  ▼
Drizzle ORM  ──  schema, queries, migrations (drizzle-kit)
  ▼
Database (SQL, configured through Drizzle)
```

### Suggested source layout

The scaffold currently contains only `src/index.ts`. A natural fit for the chosen stack is:

```
src/
├── index.ts              # Bun entrypoint: builds the Hono app, starts the server
├── app.ts                # createApp(): mounts routes and middleware
├── env.ts                # runtime config/env validation (Zod)
├── db/
│   ├── client.ts         # Drizzle client (drizzle-orm)
│   ├── schema.ts         # tables + relations
│   └── migrations/       # generated by drizzle-kit
├── auth/
│   ├── index.ts          # Better Auth instance + Drizzle adapter
│   └── middleware.ts     # session/role guards
├── modules/
│   └── restaurants/      # routes + service + schemas per domain
└── lib/
    ├── openapi.ts        # OpenAPIHono app + document config
    └── errors.ts         # error mapping using http-status-codes
```

### Request lifecycle

1. Bun receives the request and hands it to the Hono app exported from `src/index.ts`.
2. Hono middleware resolves the Better Auth session (cookie/header) and attaches the user to the
   request context.
3. An `@hono/zod-openapi` route validates params, query, and body, then invokes the handler.
4. The handler calls a domain service, which uses Drizzle to read/write the database.
5. Responses are serialized against the route's response schema; failures map to status codes from
   `http-status-codes` and a consistent JSON error shape.

## Runtime and tooling

| Tool | Declared | Resolved | Role |
| --- | --- | --- | --- |
| Bun | (runtime) | — | Executes TypeScript directly, runs `bun run --watch`, installs packages, resolves `bun.lock`. |
| TypeScript | `^7` (peer) | `7.0.2` | Type checking via `bunx tsc --noEmit`; type-only dependency, not bundled. |
| `@types/bun` | `latest` (dev) | `1.4.4` | Bun globals and API typings (`Bun.serve`, `bun:test`, etc.). |
| `drizzle-kit` | `^1.0.0-rc.5` (dev) | `1.0.0-rc.5-ab785fc` | CLI that generates SQL migrations from the Drizzle schema and applies them. Never shipped at runtime. |

### Scripts

| Script | Command | Purpose |
| --- | --- | --- |
| `dev` | `NODE_ENV=development bun run --watch --check ./src/index.ts` | Starts the API with hot reload and syntax checking. |
| `typecheck` | `bunx tsc --noEmit` | Full static type check, no output. |
| `db:generate` | `bunx --bun drizzle-kit generate` | Diff the schema and emit migration files. |
| `db:migrate` | `bunx --bun drizzle-kit migrate` | Apply pending migrations to the database. |
| `auth:generate` | `bun x --bun auth@latest generate` | Generate/refresh the Better Auth database schema. |

## Why these choices fit together

- **One schema language, two consumers.** Zod validates runtime input and feeds
  `@hono/zod-openapi`, so validation, TypeScript types, and the Swagger documentation cannot drift
  apart.
- **End-to-end type safety.** Drizzle's inferred row types flow into services and Hono handlers,
  while `tsc --noEmit` checks the seams during `typecheck`.
- **Auth and data share a pipeline.** The Drizzle adapter means Better Auth is just another schema
  consumer; one `db:generate`/`db:migrate` workflow covers everything.
- **Bun-only toolchain.** No bundler, ts-node, nodemon, or separate test framework is needed:
  Bun runs TS, watches files, runs scripts, and resolves dependencies.
- **Minimal surface.** No ORM decorators, no class-based framework, no config loader — the
  dependency list stays small and each package has a single clear responsibility.

## Configuration expectations

Runtime configuration should be validated at startup with Zod rather than read ad hoc. Likely
variables as the app grows:

| Variable | Used by | Purpose |
| --- | --- | --- |
| `DATABASE_URL` | `drizzle-orm`, `drizzle-kit` | Database connection string. |
| `BETTER_AUTH_SECRET` | `better-auth` | Signing/encryption secret for sessions. |
| `BETTER_AUTH_URL` | `better-auth` | Public base URL used in auth callbacks/cookies. |
| `NODE_ENV` | app, Better Auth | Environment mode; set to `development` by the `dev` script. |

## Working with the stack

```bash
bun install          # install/refresh dependencies from bun.lock
bun run dev          # start with watch mode
bun run typecheck    # static type check

# after editing the Drizzle schema
bun run db:generate  # create migration SQL
bun run db:migrate   # apply migrations
bun run auth:generate  # regenerate Better Auth tables if auth config changes
```
