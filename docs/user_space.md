# User Space

How identity, tenancy, and membership are modelled in this project.

Authentication is owned by **Better Auth** (`auth-schema.ts`). Everything above identity —
organizations, invitations, workspaces, and memberships — is owned by the application and lives in
`src/db/schemas/`. The two sets of tables share one database and one Drizzle migration pipeline
(`drizzle.config.ts` reads both `./src/db/schemas` and `./auth-schema.ts`).

## Mental model

```
user  (Better Auth identity, text id)
 │
 ├── session / account / verification   (auth plumbing)
 │
 └── organization_members  ── role: owner | admin | member
        │  (unique per organization + user)
        │
        ├── organization_invitations   (pending offer to join an organization)
        │
        └── workspace_members ── role: admin | member
               │  (unique per organization_member + workspace)
               │
               └── workspaces  ── belongs to exactly one organization
                      (the operational unit: a venue, kitchen, floor, …)
```

- **User** — a human. Created and authenticated by Better Auth; the app never creates `user` rows
  directly.
- **Organization** — the tenant/account boundary. A restaurant group, a hotel company, a single
  independent venue. Owned collectively through `organization_members` (there is no `owner_id`
  column on `organizations`).
- **Workspace** — one operational unit inside an organization (a specific venue or department).
  Operational domain data is expected to hang off `workspace_id`, not `organization_id`.
- **Membership is two-tier.** You cannot be a workspace member without first being an organization
  member: `workspace_members.organization_member_id` points at `organization_members.id`, not at
  `user.id`.

Consequence: a user's permissions are the *intersection* of their organization role and their
per-workspace role, and every workspace query can be resolved through the organization membership
row.

## Auth tables (`auth-schema.ts`)

These are generated by `bun run auth:generate`. Do not hand-edit them; regenerate instead.

### `account`

Stores credentials and OAuth links. Email/password users get one row with `provider_id =
'credential'` and the **hashed** password in `password`; OAuth users get provider tokens here.

| Column | Notes |
| --- | --- |
| `id` | `text` PK |
| `account_id`, `provider_id` | Provider-side identity and provider name |
| `user_id` | → `user.id`, `ON DELETE CASCADE`, indexed |
| `access_token`, `refresh_token`, `id_token`, `scope` | OAuth material |
| `access_token_expires_at`, `refresh_token_expires_at` | |
| `password` | Hashed credential, never returned to clients |
| `created_at` / `updated_at` | |

### `verification`

Short-lived verification records (email verification, password reset). Indexed on
`identifier`. Rows are disposable and expire via `expires_at`; nothing in the app should treat them
as durable state.

> **Sessions carry no tenant context.** There is no "active organization" column on `session` or
> `user`. The current organization/workspace must be resolved from the request (route param or
> header) and authorized against `organization_members` / `workspace_members` on every request.

## Domain tables (`src/db/schemas/`)

Domain tables use `snakeCase.table(...)`, so TypeScript properties are camelCase and database
columns are snake_case. `organizations` and `workspaces` include the shared `trackChanges` columns
(`created_at`, `updated_at`, both `timestamptz NOT NULL DEFAULT now()`, with `updated_at` refreshed
on write).

### `organizations` — `organizations.ts`

| Column | Type | Notes |
| --- | --- | --- |
| `id` | `uuid` PK default `gen_random_uuid()` | |
| `name` | `varchar(100)` not null | |
| `slug` | `varchar(150)` not null unique | Globally unique across all organizations |
| `logo` | `text` | |
| `description` | `text` | |
| `created_at` / `updated_at` | `timestamptz` not null | `trackChanges` |

Zod exports:

- `insertOrganizationSchema` — omits `id`, `slug`, `createdAt`, `updatedAt`. **Slug is
  server-generated** (`slugify` + `nanoid` suffix); clients never send it.
- `updateOrganizationSchema` — `pick({ id, name, logo, description })`.
- `selectOrganizationSchema` — full row.

There is no `ownerId`. Ownership is the `organization_members` row with `role = 'owner'`.

### `organization_members` — `organizationMembers.ts`

| Column | Type | Notes |
| --- | --- | --- |
| `id` | `uuid` PK | Referenced by `workspace_members` |
| `organization_id` | `uuid` not null → `organizations.id` | `ON DELETE CASCADE` |
| `user_id` | `text` not null → `user.id` | `ON DELETE CASCADE` |
| `role` | `organization_roles` not null default `'member'` | Enum: `owner`, `admin`, `member` |
| `joined_at` | `timestamptz` not null default `now()` | |
| `added_by` | `text` → `user.id` | `ON DELETE SET NULL` |

Unique: `organization_members_unique (organization_id, user_id)` — one membership row per user per
organization.

Zod exports: `insertOrganizationMemberSchema` (role overridden with `z.enum(ogMemberRoles)`; omits
`id`, `joinedAt`), `updateOrganizationMemberSchema` (`pick({ id, role })`), plus `ogMemberRoles` and
the pg enum exported as `roleEnum`.

### `organization_invitations` — `organizationInvitations.ts`

| Column | Type | Notes |
| --- | --- | --- |
| `id` | `uuid` PK | |
| `organization_id` | `uuid` not null → `organizations.id` | `ON DELETE CASCADE` |
| `invited_by` | `text` **not null** → `user.id` | The inviter; `ON DELETE CASCADE` |
| `invited_user_email` | `varchar(255)` not null | The invitee's email address (normalized, lowercase) |
| `status` | `organization_invitation_status` not null default `'pending'` | `pending`, `accepted`, `declined`, `expired`, `revoked` |
| `expires_at` | `timestamptz` not null | |
| `accepted_at` | `timestamptz` | Set when accepted |
| `created_at` | `timestamptz` not null default `now()` | |

Partial unique index: `organization_invitations_pending_unique (organization_id,
invited_user_email) WHERE status = 'pending'` — at most one **live** invitation per address per
organization. Accepted, declined, expired, and revoked rows are kept as history, so inviting the
same address again after one of those outcomes inserts a new row instead of overwriting the old one.

There is no scheduler: a `pending` row whose `expires_at` has passed is treated as expired by
queries (`expires_at > now()`), and should be transitioned to `expired` lazily when invitations are
listed or a new invite is sent.

Zod exports use the plain factory output (no `.omit`/`.pick`), so the insert schema still exposes
`id`, `invitedBy`, `status`, `acceptedAt`, and `createdAt`. Route-level schemas should narrow these.

The invitation is keyed by `invited_user_email`, not by a user id, so the invitee does **not** need
an account at invite time. The matching account is resolved when the invitation is accepted (by
email) or displayed (pending invitations for the current user).

`invited_by` records the inviter and is set by the server from the session, never by the client. It
cascades with the inviter's account: deleting the inviter removes the invitations they issued.

| `name` | `varchar(100)` not null | |
| `slug` | `varchar(150)` not null unique | Globally unique across all workspaces |
| `description` | `text` | |
| `created_by` | `text` → `user.id` | `ON DELETE SET NULL`; not constrained to be a member |
| `created_at` / `updated_at` | `timestamptz` not null | `trackChanges` |

Zod exports:

- `insertWorkspaceSchema` — omits `id`, `slug`, `createdBy`, `createdAt`, `updatedAt`; requires
  `organizationId` and `name`.
- `updateWorkspaceSchema` — `pick({ id, name, description })`. `organizationId` is intentionally
  immutable here.
- `selectWorkspaceSchema` — full row.

### `workspace_members` — `workspaceMembers.ts`

| Column | Type | Notes |
| --- | --- | --- |
| `id` | `uuid` PK | |
| `workspace_id` | `uuid` not null | One half of the composite FK to `workspaces (id, organization_id)` |
| `organization_member_id` | `uuid` not null | One half of the composite FK to `organization_members (id, organization_id)` |
| `organization_id` | `uuid` not null | Tenant key; must match **both** the workspace's and the member's organization |
| `role` | `workspace_roles` not null default `'member'` | Enum: `admin`, `member` |
| `joined_at` | `timestamptz` not null default `now()` | |
| `added_by` | `text` → `user.id` | `ON DELETE SET NULL` |

Unique: `workspace_members_unique (organization_member_id, workspace_id)`.

Cross-organization rows are impossible. `(workspace_id, organization_id)` references
`workspaces (id, organization_id)` and `(organization_member_id, organization_id)` references
`organization_members (id, organization_id)`; a row whose member belongs to a different organization
than the workspace violates one of the two composite FKs. The parent tables therefore carry
`workspaces_id_organization_id_unique` and `organization_members_id_organization_id_unique`.

A further consequence: `workspaces.organization_id` cannot be changed while workspace members exist —
the composite FK rejects the update instead of silently orphaning rows. Move a workspace between
organizations by deleting/migrating its members first.

Zod exports: `insertWorkspaceMemberSchema` (role overridden with `z.enum(workspaceRoles)`; omits
`id`, `joinedAt`, and `organizationId`, which the service derives from the workspace),
`upadteWorkspaceMemberSchema` (**sic** — typo in the exported name, `pick({ id, role })`),
`workspaceRoles`, and the enum exported as `roleEnum`.

There is no `owner` workspace role. The organization `owner` is expected to be implicitly
authorized on every workspace in the organization.

## Relationship summary

| Relationship | Cardinality | Delete behavior |
| --- | --- | --- |
| `user` → `session` | 1:N | cascade |
| `user` → `account` | 1:N | cascade |
| `organizations` → `organization_members` | 1:N | cascade |
| `user` → `organization_members` | 1:N | cascade |
| `organizations` → `organization_invitations` | 1:N | cascade |
| `user` → `organization_invitations` (as inviter) | 1:N | cascade |
| `organizations` → `workspaces` | 1:N | cascade |
| `organization_members` → `workspace_members` | 1:N | cascade (composite key with `organization_id`) |
| `workspaces` → `workspace_members` | 1:N | cascade (composite key with `organization_id`) |

Only the Better Auth tables declare Drizzle `relations()` (`userRelations`, `sessionRelations`,
`accountRelations`). **No domain schema exports relations**, so `db.query.organizations...`-style
relational queries are unavailable; use explicit `join`s (or add relations before relying on the
relational API).

## Role model

| Organization role | Intended capability |
| --- | --- |
| `owner` | Full control: update/delete organization, manage admins, all workspaces, billing |
| `admin` | Manage members and workspaces, all workspace content |
| `member` | Belongs to the organization; only sees workspaces they were explicitly added to |

| Workspace role | Intended capability |
| --- | --- |
| `admin` | Manage workspace settings and workspace membership |
| `member` | Operate inside the workspace per the domain permissions of the app |

Effective access rule (recommended, not yet enforced anywhere):

```
canAccessWorkspace(user, workspace) =
     exists organization_members m
       where m.user_id = user.id
         and m.organization_id = workspace.organization_id
         and (
              m.role in ('owner', 'admin')
              or exists workspace_members wm
                   where wm.organization_member_id = m.id
                     and wm.workspace_id = workspace.id
         )
```

### Route-level permission enforcement

Permissions are declared per role in `src/utils/roles-permissions/` and checked with
`checkLevelPermissions({ level, permission, organizationRole, workspaceRole })`, whose roles must
come from membership rows, never client input. Enforcement is route-by-route as domains are built:

- `PATCH /organizations/{id}` and `PUT /organizations/{id}/logo` require the organization-level
  `organization:update` permission (only `owner` grants it today). Non-members get `404` (no
  existence leak); members without the grant get `403`. The membership role is resolved via
  `OrganizationsService.getOrganizationById`, which returns the caller's `organization_members`
  row alongside the organization.

## Canonical flows

### 1. Sign up / sign in

Handled entirely by Better Auth. It creates the `user` row and, for email/password, the
`account` row with a hashed password, then issues a `session` row whose `token` is stored in the
cookie. The app receives the resolved session (user id + session id) from the auth handler.

### 2. Create an organization

One transaction, because ownership lives in a second table:

1. Generate `slug` from `name` (unique, retry on conflict).
2. `INSERT organizations (name, slug, logo?, description?)`.
3. `INSERT organization_members (organization_id, user_id, role: 'owner', added_by: user.id)`.

If step 3 is skipped or later deleted, the organization is orphaned: nothing in the schema requires
it to have any member.

### 3. Create a workspace

1. Verify the caller is `owner` or `admin` in `workspace.organizationId`.
2. Generate a globally unique `slug` from `name`.
3. `INSERT workspaces (organization_id, name, slug, description?, created_by: user.id)`.
4. Optionally insert a `workspace_members` row for the creator's organization membership so they
   appear in workspace member lists (`role: 'admin'` is the sensible default for an org owner).

### 4. Invite a user to the organization

1. Verify the caller is `owner` or `admin` in the organization.
2. Normalize the invited address (trim + lowercase) into `invited_user_email`.
3. Reject the invite if the address already belongs to a member of the organization (the database
   cannot express this check).
4. Send or resend with an upsert scoped to the pending row:

   ```ts
   await db.insert(organizationInvitations).values({
     organizationId,
     invitedBy: callerId,
     invitedUserEmail: email,
     expiresAt,
   }).onConflictDoUpdate({
     target: [
       organizationInvitations.organizationId,
       organizationInvitations.invitedUserEmail,
     ],
     targetWhere: eq(organizationInvitations.status, "pending"),
     set: { invitedBy: callerId, expiresAt, acceptedAt: null },
   });
   ```

   The conflict target is the partial index, so an existing accepted, declined, expired, or revoked
   row does **not** block the insert — a fresh pending row is created and the old one stays as
   history. Resending to an address with a still-pending invite extends that row instead of stacking
   a duplicate.
5. Notify the invitee out of band; the invitation identity is
   `(organization_id, invited_user_email)`. The invitee does not need an account yet.

Revoking: an `owner`/`admin` transitions a pending row to `revoked`, which frees the partial index
slot so the address can be invited again later.

Acceptance:

1. Match by the signed-in user's **verified** email, case-insensitively: load the invitation by
   `(organization_id, invited_user_email)` and require `status = 'pending'` and
   `expires_at > now()`.
2. `INSERT organization_members (organization_id, user_id, role: 'member', added_by:
   invitation.invited_by)` (or reuse the row if it already exists).
3. `UPDATE organization_invitations SET status = 'accepted', accepted_at = now()`.

Invitations carry no role: accepting one creates a plain `member` organization membership. Owners and
admins can promote the new member afterwards by updating `organization_members.role`.

### 5. Add an existing user directly

An `owner`/`admin` can skip the invitation flow: insert the `organization_members` row with the
desired role and `added_by` set to the acting user.

### 6. Add an organization member to a workspace

1. Resolve the target's `organization_members.id` for the target workspace's organization.
2. `INSERT workspace_members (workspace_id, organization_member_id, organization_id, role, added_by)`,
   deriving `organization_id` from the workspace (never from the client).
3. The composite FKs reject the row if the member or the workspace does not belong to that
   organization, so a service-level check is only needed for a friendlier error message.

Adding a user straight to a workspace without an organization membership is not possible — the FK
requires the membership row.

### 7. Remove / leave

- Remove from workspace → delete the `workspace_members` row.
- Remove from organization → delete the `organization_members` row; every workspace membership for
  that member is cascaded away.
- Delete a workspace → its `workspace_members` rows cascade.
- Delete an organization → members, invitations, workspaces, and (transitively) workspace members
  cascade.
- Delete a user → sessions, accounts, memberships, and invitations cascade; `added_by` and
  `created_by` references become `NULL`.

## Access-resolution queries

```ts
// Organizations the current user belongs to, with their role
db.select({ org: organizations, role: organizationMembers.role })
  .from(organizationMembers)
  .innerJoin(organizations, eq(organizations.id, organizationMembers.organizationId))
  .where(eq(organizationMembers.userId, userId));

// Workspaces explicitly assigned to the current user
db.select({ workspace: workspaces, role: workspaceMembers.role })
  .from(workspaceMembers)
  .innerJoin(workspaces, eq(workspaces.id, workspaceMembers.workspaceId))
  .innerJoin(
    organizationMembers,
    eq(organizationMembers.id, workspaceMembers.organizationMemberId),
  )
  .where(eq(organizationMembers.userId, userId));

// Membership row used for authorization checks
db.select()
  .from(organizationMembers)
  .where(
    and(
      eq(organizationMembers.userId, userId),
      eq(organizationMembers.organizationId, organizationId),
    ),
  )
  .limit(1);

// Pending invitations addressed to the current user's email
db.select()
  .from(organizationInvitations)
  .where(
    and(
      eq(organizationInvitations.invitedUserEmail, user.email),
      eq(organizationInvitations.status, "pending"),
      gt(organizationInvitations.expiresAt, new Date()),
    ),
  );

// Invitations sent by the current user
db.select()
  .from(organizationInvitations)
  .where(eq(organizationInvitations.invitedBy, userId));
```

## Constraints and invariants

Enforced by the database today:

- One membership per `(organization_id, user_id)`.
- One workspace assignment per `(organization_member_id, workspace_id)`.
- At most one **pending** invitation per `(organization_id, invited_user_email)`; rows in terminal
  statuses (`accepted`, `declined`, `expired`, `revoked`) are retained as history.
- A workspace member always belongs to the same organization as the workspace (composite FKs), and a
  workspace cannot change organization while it has members.
- Organization and workspace slugs are globally unique.
- Deleting an organization, workspace, or organization member cleans up dependent rows by cascade.
- Invitations are addressed to an email, so the invitee does not need an account to be invited.

Expected but **not** enforced:

- An organization always has at least one `owner`.
- An organization has at most one `owner` (nothing stops several).
- `workspaces.created_by` and `added_by` are members of the relevant organization.
- Stale pending invitations are transitioned to `expired` lazily on read or on the next invite; there
  is no scheduler.
- A user cannot be invited to an organization they already belong to.
- Workspace slugs are unique only globally, not per organization.

## Known gaps and follow-ups

Schema-level issues worth fixing before the module is built out:

1. **Invitation acceptance depends on email matching.** `invited_user_email` is the only link between
   an invitation and its invitee. Require a verified email at acceptance, compare case-insensitively
   (normalize on write), and decide whether to record the resulting `user_id` for auditing.
   "Already a member" is not prevented at the DB level and must be checked in the service.
2. **No scheduled expiry sweep.** `expired` and `revoked` statuses exist, but nothing moves stale
   `pending` rows on a timer; do it lazily when listing or inviting, or add a job. Consider a
   `declined_at`/`revoked_at` or a single `responded_at` column if the UI shows outcomes.
3. **Duplicate `roleEnum` export.** Both `organizationMembers.ts` and `workspaceMembers.ts` export a
   symbol named `roleEnum`; a re-export barrel will collide. Rename them
   (`organizationRoleEnum`, `workspaceRoleEnum`).
4. **Zod schemas leak server-managed fields.** `insertOrganizationInvitationSchema` and the member
   insert schemas accept `status`, `id`, `invitedBy`, `addedBy`, and `role: 'owner'`. Strip or
   overwrite these at the route layer; never trust `invitedBy`/`addedBy` from a client.
5. **No domain relations.** Add Drizzle `relations()` for organizations, members, invitations,
   workspaces, and workspace members if the relational query API (and `db.query`) is preferred over
   manual joins.
6. **Missing indexes.** Add `organization_members (user_id)` (currently only covered as the second
   column of the unique index), `organization_invitations (invited_user_email, status)`,
   `organization_invitations (invited_by)`, `workspaces (organization_id)`,
   `workspace_members (workspace_id)`, and `workspace_members (organization_id)`. The partial
   pending index already covers `(organization_id, invited_user_email)` for pending rows.
7. **Orphan risk on ownership.** With ownership expressed only as a member row, deleting the last
   owner (or the owner's account) leaves an organization nobody can administer. Enforce "at least
   one owner" in the service layer, or transfer ownership explicitly on removal.
8. **Naming inconsistency for the workspace member update schema.**
   `upadteWorkspaceMemberSchema` is misspelled and should be `updateWorkspaceMemberSchema`.
9. **Operational data is not attached yet.** No current table references `workspace_id`. When
   catalog/floor/orders land, every one of them should carry a `workspace_id` FK (the tenant key),
   and every query must be scoped by an authorized workspace.
