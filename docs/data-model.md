# Data Model

How identity, tenancy, membership, and audit are modelled.

Authentication is owned by **Better Auth** (`auth-schema.ts`, generated — never hand-edit;
regenerate with `bun run auth:generate`). Everything above identity — organizations, invitations,
workspaces, memberships, and activity logs — is owned by the application and lives in
`src/db/schemas/`. Both sets of tables share one database and one Drizzle migration pipeline
(`drizzle.config.ts` reads `./src/db/schemas` and `./auth-schema.ts`).

## Mental model

```
user  (Better Auth identity, text id)
 │
 ├── session / account / verification   (auth plumbing)
 │
 └── organization_members  ── role: owner | admin | member
        │  (unique per organization + user)
        │
        ├── organization_invitations   (pending offer to join an organization)
        │
        └── workspace_members ── role: admin | member
               │  (unique per organization_member + workspace; composite FKs pin
               │   both the workspace and the member to the same organization)
               │
               └── workspaces  ── belongs to exactly one organization
                      (the operational unit; all future domain data hangs off workspace_id)

activity_logs  ── append-only audit feed, scoped to organization (+ optional workspace)
```

- **User** — a human. Created and authenticated by Better Auth; the app never inserts `user` rows
  directly (test factories are the exception).
- **Organization** — the tenant/account boundary (a restaurant group or single venue). Ownership is
  expressed through `organization_members` rows with `role = 'owner'`; there is no `owner_id`
  column.
- **Workspace** — one operational unit inside an organization (a venue or department). Operational
  domain data hangs off `workspace_id`, not `organization_id`.
- **Membership is two-tier.** `workspace_members.organization_member_id` points at
  `organization_members.id`, not at `user.id`: no workspace membership without organization
  membership. A user's effective workspace access is the combination of their organization role and
  their per-workspace role.
- **Sessions carry no tenant.** The active organization/workspace is resolved per request from the
  `x-organization-id` / `x-workspace-id` headers and authorized against the membership tables.

## Auth tables (`auth-schema.ts`)

Generated by `bun run auth:generate` from `src/auth.ts` (email/password, `username()` and
`openAPI()` plugins, required `firstName`/`lastName` additional fields, 24h sessions refreshed
after 5 minutes).

### `user`

| Column | Type | Notes |
| --- | --- | --- |
| `id` | `text` PK | Better Auth identifier; every domain FK to a user is `text` |
| `name` | `text` not null | Display name |
| `email` | `text` not null unique | Login identifier |
| `email_verified` | `boolean` not null default `false` | |
| `image` | `text` | Profile image path/URL |
| `username` | `text` unique | Optional; stored lowercase (username plugin) |
| `display_username` | `text` | Optional; the typed casing |
| `first_name`, `last_name` | `text` not null | Required additional fields captured at sign-up |
| `created_at` / `updated_at` | `timestamp` not null | Supplied by Better Auth |

### `session`

`token` (unique, carried in the cookie), `expires_at`, `ip_address`, `user_agent`,
`user_id → user.id` (`ON DELETE CASCADE`, indexed), plus timestamps.

### `account`

Credentials and OAuth links. Email/password users get one row with `provider_id = 'credential'`
and the hashed password in `password`; OAuth users get provider tokens here. `user_id → user.id`
(`ON DELETE CASCADE`, indexed). The password hash never leaves the server.

### `verification`

Short-lived records (email verification, password reset), indexed on `identifier`, expired via
`expires_at`. Disposable state — nothing should treat it as durable.

## Domain tables (`src/db/schemas/`)

Domain tables use `snakeCase.table(...)`: camelCase in TypeScript, snake_case in SQL. Mutable
aggregates include the shared `trackChanges` columns (`created_at` / `updated_at`, both
`timestamptz NOT NULL DEFAULT now()`, `updated_at` refreshed on write). Each schema file exports
the table, `selectXSchema` / `insertXSchema` (server-managed fields omitted) / `updateXSchema`
(mutable fields picked), and `X` / `InsertX` types. Zod is built with
`createSchemaFactory({ zodInstance: z })` importing `z` from `@hono/zod-openapi`.

### `organizations` — `organizations.ts`

| Column | Type | Notes |
| --- | --- | --- |
| `id` | `uuid` PK default random | |
| `name` | `varchar(100)` not null | |
| `slug` | `varchar(150)` not null unique | Globally unique; server-generated (`slugify` + `nanoid` suffix, retried on conflict) |
| `logo` | `text` | Stored asset path under `static/organizations/logos` |
| `description` | `text` | |
| `created_at` / `updated_at` | `timestamptz` not null | `trackChanges` |

`insertOrganizationSchema` omits `id`, `slug`, `createdAt`, `updatedAt` — clients never send slugs.

### `organization_members` — `organizationMembers.ts`

| Column | Type | Notes |
| --- | --- | --- |
| `id` | `uuid` PK | Referenced by `workspace_members` (composite FK) |
| `organization_id` | `uuid` not null → `organizations.id` | `ON DELETE CASCADE` |
| `user_id` | `text` not null → `user.id` | `ON DELETE CASCADE` |
| `role` | `organization_roles` not null default `'member'` | Enum: `owner`, `admin`, `member` |
| `joined_at` | `timestamptz` not null default `now()` | |
| `added_by` | `text` → `user.id` | `ON DELETE SET NULL`; set by the server, never the client |

Unique: `(organization_id, user_id)` — one membership per user per organization. Also carries the
composite `(id, organization_id)` unique key consumed by `workspace_members`.

### `organization_invitations` — `organizationInvitations.ts`

| Column | Type | Notes |
| --- | --- | --- |
| `id` | `uuid` PK | |
| `organization_id` | `uuid` not null → `organizations.id` | `ON DELETE CASCADE` |
| `invited_by` | `text` not null → `user.id` | The inviter; `ON DELETE CASCADE`; set from the session |
| `invited_user_email` | `varchar(255)` not null | Normalized (lowercase) invitee address |
| `status` | `organization_invitation_status` not null default `'pending'` | `pending`, `accepted`, `declined`, `expired`, `revoked` |
| `expires_at` | `timestamptz` not null | |
| `accepted_at` | `timestamptz` | Set when accepted |
| `created_at` | `timestamptz` not null default `now()` | |

Partial unique index: `(organization_id, invited_user_email) WHERE status = 'pending'` — at most
one **live** invitation per address per organization. Terminal-status rows are kept as history, so
re-inviting inserts a fresh pending row instead of overwriting.

The invitation is keyed by email, so the invitee does **not** need an account at invite time; the
account is matched by email (case-insensitive) when the invitation is accepted — the
`email_verified` flag is not enforced until a verification flow exists.

There is no scheduler: a `pending` row past `expires_at` is expired lazily on read/next invite.

> The table is served by `OrganizationInvitationsService` (`getOrganizationInvitations`,
> `getOrganizationInvitation`, `sendInvite`, `revokeInvite`, `acceptInvite`) and mounted routes
> (`GET /invitations`, `POST /organizations/{organizationId}/invitations/{invitationId}/accept`,
> `GET|POST /organization/invitations`,
> `POST /organization/invitations/{invitationId}/revoke`). Its insert
> Zod schema is also not narrowed — it still exposes `id`, `invitedBy`, `status`, `acceptedAt`,
> `createdAt` — so route-level schemas must narrow these before use (see Known gaps).

### `workspaces` — `workspaces.ts`

| Column | Type | Notes |
| --- | --- | --- |
| `id` | `uuid` PK | Intended owner key for all future operational rows |
| `organization_id` | `uuid` not null → `organizations.id` | `ON DELETE CASCADE` |
| `name` | `varchar(100)` not null | |
| `slug` | `varchar(150)` not null unique | Globally unique; server-generated like organization slugs |
| `description` | `text` | |
| `created_by` | `text` → `user.id` | `ON DELETE SET NULL`; not constrained to be a member |
| `created_at` / `updated_at` | `timestamptz` not null | `trackChanges` |

Also carries the composite `(id, organization_id)` unique key. `organizationId` is immutable in
`updateWorkspaceSchema` (`pick({ id, name, description })`) — and effectively unchangeable while
workspace members exist, because the composite FK from `workspace_members` rejects the update.

### `workspace_members` — `workspaceMembers.ts`

| Column | Type | Notes |
| --- | --- | --- |
| `id` | `uuid` PK | |
| `workspace_id` | `uuid` not null | Half of the composite FK to `workspaces (id, organization_id)` |
| `organization_member_id` | `uuid` not null | Half of the composite FK to `organization_members (id, organization_id)` |
| `organization_id` | `uuid` not null | Tenant key; must match **both** the workspace and the member |
| `role` | `workspace_roles` not null default `'member'` | Enum: `admin`, `member` (no owner role) |
| `joined_at` | `timestamptz` not null default `now()` | |
| `added_by` | `text` → `user.id` | `ON DELETE SET NULL` |

Unique: `(organization_member_id, workspace_id)`. Cross-organization rows are impossible: both
composite FKs must agree on `organization_id`. `insertWorkspaceMemberSchema` omits
`organizationId` (the service derives it from the workspace).

Known naming issue: the update schema is exported as `upadteWorkspaceMemberSchema` (**sic**), and
both member schema files export a symbol named `roleEnum` (see Known gaps).

### `activity_logs` — `activityLogs.ts`

Append-only audit feed — no `trackChanges`, no updates, ever.

| Column | Type | Notes |
| --- | --- | --- |
| `id` | `bigserial` PK | Ordering key |
| `organization_id` | `uuid` not null → `organizations.id` | `ON DELETE CASCADE` |
| `workspace_id` | `uuid` → `workspaces.id` | Nullable; `ON DELETE SET NULL` (single-column FK on purpose — a composite FK with `SET NULL` would also null the `NOT NULL` organization key) |
| `actor_user_id` | `text` → `user.id` | Nullable (`ON DELETE SET NULL`); null for non-user actors |
| `actor_label` | `varchar(150)` not null | Snapshot of the actor's name; survives rename/delete |
| `source` | `varchar(20)` not null default `'api'` | |
| `action` | `varchar(32)` not null | Legal verbs come from the entity's activity definition |
| `entity_type` / `entity_id` | `varchar(64)` / `text` not null | What changed |
| `summary` | `text` not null | Rendered once at write time; never regenerated |
| `changes` | `jsonb` | Field-level diff `{ field: { from, to } }` built from the definition's allowlist |
| `metadata` | `jsonb` | Optional context |
| `created_at` | `timestamptz` not null default `now()` | |

Indexes: `(organization_id, id desc)`, `(workspace_id, id desc)`,
`(entity_type, entity_id, id desc)`, `(actor_user_id, id desc)`.

Rows are written via `ActivityLogger` (see [Audit](#audit) below), constructed with the same
executor as the mutation so the audit row commits or rolls back with it.

## Relationship summary

| Relationship | Cardinality | Delete behavior |
| --- | --- | --- |
| `user` → `session` / `account` | 1:N | cascade |
| `organizations` → `organization_members` | 1:N | cascade |
| `user` → `organization_members` | 1:N | cascade |
| `organizations` → `organization_invitations` | 1:N | cascade |
| `user` → `organization_invitations` (as inviter) | 1:N | cascade |
| `organizations` → `workspaces` | 1:N | cascade |
| `organization_members` → `workspace_members` | 1:N | cascade (composite with `organization_id`) |
| `workspaces` → `workspace_members` | 1:N | cascade (composite with `organization_id`) |
| `organizations` → `activity_logs` | 1:N | cascade |
| `workspaces` → `activity_logs` | 1:N | set null |
| `user` → `activity_logs` (as actor) | 1:N | set null |

Only the Better Auth tables declare Drizzle `relations()`. No domain schema exports relations, so
`db.query.*` relational queries are unavailable — use explicit joins (this also keeps tenant
scoping explicit at every query site).

## Roles and permissions

| Organization role | Intended capability |
| --- | --- |
| `owner` | Full control: update/delete organization, manage members/invitations, create/manage workspaces, billing |
| `admin` | Manage members and workspaces, all workspace content |
| `member` | Belongs to the organization; only reaches workspaces explicitly assigned |

| Workspace role | Intended capability |
| --- | --- |
| `admin` | Manage workspace settings and membership; full operational access (catalog, floor, orders, kitchen, inventory, staff, payments, reports) |
| `member` | Operate inside the workspace per granted domain permissions |

Permissions are namespaced strings (`resource:action` / `resource:sub:action`) declared per role in
`src/utils/roles-permissions/`:

- `organizationPermissions` — keyed by organization role, kept in sync with the `organization_roles`
  enum. Only `owner` has grants today; `admin`/`member` exist as keys with empty lists.
- `workspacePermissions` — keyed by workspace role (`admin`, `member`). Only `admin` has grants.
- `checkLevelPermissions({ level, permission, organizationRole, workspaceRole })` checks at
  `organization`, `workspace`, or `organizationWorkspace` level (the last grants when **either**
  level grants it, since organization owners implicitly reach every workspace). It returns `false`
  when the role needed for the level is missing or unknown. Roles always come from membership rows,
  never client input.

Effective access rule, as implemented in `workspaceRoleMiddleware`:

```
organization owner        → implicit workspace role 'admin' on every workspace
                            of their organization (no workspace_members row needed)
organization admin/member → must have a workspace_members row
```

Enforcement status:

- `PATCH /organizations/{id}` and `PUT /organizations/{id}/logo` enforce `organization:update`
  (organization level, from the caller's membership row). Non-members get 404 (no existence leak);
  members without the grant get 403.
- `PATCH /workspaces/{id}` enforces `workspace:update` at `organizationWorkspace` level using both
  the caller's organization and workspace membership rows.
- `GET /organization/invitations`, `POST /organization/invitations`, and
  `POST /organization/invitations/{invitationId}/revoke` enforce
  `organization:invitation:read` / `organization:member:invite` /
  `organization:invitation:revoke` declaratively via `requireLevelPermissions` route middleware;
  the organization is addressed only by the `x-organization-id` header (no path param), so the
  header is the single source of truth and non-members/unknown organizations get 403. The invitee
  inbox (`GET /invitations`) needs no permission and no tenant header — it is session-scoped (an
  invitee is not a member yet) and only ever returns the session user's own invitations.

## Tenant middleware chain

`src/middlewares/` (wired in `src/v1/api/index.ts`; only route mounts registered **after** the
`use(...)` lines are guarded — the organization-scoped invitation routes, mounted between the two
`use(...)` lines, are the first consumers and address the organization only through the
`x-organization-id` header):

1. `authMiddleware` — resolves the Better Auth session; sets context `user`/`session`; otherwise
   401 `NOT_SIGNED_IN`.
2. `organizationMemberMiddleware` — reads `x-organization-id` (must be a UUID, else
   `ForbiddenError`), loads the caller's `organization_members` row, sets context
   `userOrganizationMember`, or 403 when missing/not a member.
3. `workspaceRoleMiddleware` — reads `x-workspace-id`, fetches the workspace through
   `WorkspacesService.getWorkspaceById`, rejects when the workspace is missing or belongs to a
   different organization (this is what keeps the owner short-circuit from leaking across
   organizations), then sets context `userWorkspaceMemberRole` — `admin` for owners, the
   `workspace_members` role otherwise, or 403.

Order matters: `workspaceRoleMiddleware` reads the membership row
`organizationMemberMiddleware` sets.

## Canonical flows

### 1. Sign up / sign in

Handled entirely by Better Auth through `src/v1/api/routes/auth.ts`, which calls
`auth.api.signUpEmail` / `auth.api.signInEmail` and copies `Set-Cookie` headers onto the response.
Sign-up creates the `user` row plus the `account` row with the hashed password, and issues a
`session` row.

### 2. Account setup — two entry points, one orchestrator

`AccountsService.create({ userId, organization, workspace? })` composes
`OrganizationsService.createOrganization` and `WorkspacesService.createWorkspace`:

1. Create the organization — server-generated slug, caller inserted as `owner` member
   (`added_by` = self), in one transaction.
2. Create a default workspace in it — name defaults to the organization name, caller added as
   workspace `admin` member, `workspace.created` audit row written on the same transaction.
3. Returns `{ organization, workspace }`.

Entry points:

- `POST /api/v1/auth/account` (public) — signs the user up first, then runs the orchestrator with
  the new user id; session cookies are attached on success.
- `POST /api/v1/organizations/account` (signed-in) — runs the orchestrator with the session user.

### 3. Create a workspace (standalone)

`WorkspacesService.createWorkspace` requires an organization membership (returns `null` without
one), generates the slug with conflict retry, inserts the workspace, adds the creator as workspace
`admin`, and writes the `workspace.created` audit row — all on one transaction.

### 4. Update an organization / workspace

- The route fetches the entity together with the caller's membership rows
  (`getOrganizationById` / `getWorkspaceById`), maps non-membership to 404, checks
  `checkLevelPermissions`, then updates.
- A changed name regenerates the slug (conflict retry). The mutation and its
  `organization.updated` / `workspace.updated` audit row run on the same transaction, diffed
  against the pre-update row.
- No-change requests return the current row.

### 5. Invitations (send/list/revoke/accept shipped as routes)

Intended lifecycle, per the schema:

1. Verify the caller may invite; normalize the address to lowercase into `invited_user_email`.
2. Reject if the address already belongs to a member (service-level check; the DB cannot express
   it).
3. Send/resend with an upsert scoped to the pending row (`onConflictDoUpdate` targeting
   `(organization_id, invited_user_email)` with `targetWhere: status = 'pending'`), so a
   still-pending invite is extended and terminal rows are kept as history.
4. Expire lazily: pending rows past `expires_at` are treated as expired on read.
5. Acceptance (`POST /organizations/{organizationId}/invitations/{invitationId}/accept`, backed by
   `OrganizationInvitationsService.acceptInvite`): match the signed-in user's account email
   case-insensitively — wrong addressee is rejected (`ForbiddenError`; the `email_verified` flag is
   not enforced until a verification flow exists), require `pending` and unexpired, insert the
   `organization_members` row (plain `member`, `added_by` null, via
   `OrganizationMembersService.addOrganizationMember`), then set `status = 'accepted'`,
   `accepted_at = now()` — all in one transaction, with `invitation.accepted` and `member.created`
   audit rows. Not pending / expired / already a member raise conflicts. Promote roles afterwards.
6. Revoke: transition a pending row to `revoked`, freeing the partial-index slot.

### 6. Add / remove members

- Adding an existing user directly (org or workspace level) inserts the membership row with the
  desired role and `added_by` from the acting user. Workspace additions require the target's
  `organization_members.id` — the composite FKs make it impossible to add a workspace member who
  is not an organization member.
- Removal cascades: deleting an organization member removes all their workspace memberships;
  deleting an organization cascades members, invitations, workspaces, workspace members, and
  activity logs; deleting a user cascades sessions/accounts/memberships and nulls `added_by`,
  `created_by`, `actor_user_id`.

## Access-resolution queries

```ts
// Organizations the user belongs to
inArray(organizations.id,
  db.select({ organizationId: organizationMembers.organizationId })
    .from(organizationMembers).where(eq(organizationMembers.userId, userId)));

// Caller's membership row for authorization (used by getOrganizationById)
innerJoin(organizationMembers, and(
  eq(organizationMembers.organizationId, organizations.id),
  eq(organizationMembers.userId, userId),
));

// Workspaces the user can reach through organization membership (getWorkspaces)
// and the workspace + both membership rows for one workspace (getWorkspaceById,
// left join on workspace_members so non-members still resolve the workspace).

// Pending invitations addressed to the user's email
eq(organizationInvitations.invitedUserEmail, user.email),
eq(organizationInvitations.status, "pending"),
gt(organizationInvitations.expiresAt, new Date());
```

## Audit

Every state change should write an `activity_logs` row via `ActivityLogger` (constructed with the
same executor/transaction as the mutation):

- `record(input)` inserts one frozen row (caller supplies tenant scope, actor snapshot, rendered
  summary, diff payload).
- `recordChange(definition, input)` is the normal path: it validates the action against the
  entity's definition, renders the summary (`definition.summarize` or a default), and builds the
  field-level diff from the definition's `diff` allowlist unless the caller overrides them.

Definitions live in `src/utils/activityDefinitions.ts`, built with `defineActivity<TEntity>()` —
typed so the `diff` allowlist references real entity fields and a typo in `action` fails at compile
time. Defined today: `organizationActivity`, `workspaceActivity`, `organizationInvitationActivity`,
and `organizationMemberActivity` (diffs over their mutable fields).

Current writers: `OrganizationsService.updateOrganization` (`organization.updated`),
`WorkspacesService.createWorkspace` (`workspace.created`) and `updateWorkspace`
(`workspace.updated`), `OrganizationInvitationsService.sendInvite`
(`invitation.created`) and `acceptInvite` (`invitation.accepted`, `member.created`), and
`OrganizationMembersService.updateOrganizationRole` (`organization_member.updated`).

## Constraints and invariants

Enforced by the database today:

- One organization membership per `(organization_id, user_id)`; one workspace membership per
  `(organization_member_id, workspace_id)`.
- At most one pending invitation per `(organization_id, invited_user_email)`.
- A workspace member always belongs to the same organization as the workspace (composite FKs);
  a workspace cannot change organization while it has members.
- Organization and workspace slugs are globally unique.
- Deleting an organization/workspace/member cleans up dependents by cascade; user references in
  `added_by` / `created_by` / `actor_user_id` become `NULL`.
- Activity rows are append-only (no unique constraints to violate, no updates).

Expected but **not** enforced:

- An organization always has at least one `owner` (and at most one).
- `workspaces.created_by` / `added_by` / `invited_by` refer to members of the relevant organization.
- A user cannot be invited to an organization they already belong to.
- Workspace slugs are unique only globally, not per organization.

## Known gaps and follow-ups

1. **Invitation acceptance is unimplemented.** When built, it must require a verified email,
   compare case-insensitively (normalized on write), and check "not already a member" in the
   service.
2. **Member routes are minimal.** `OrganizationMembersService`
   (`getOrganizationMembers`, `updateOrganizationRole`) is mounted only through
   `GET /organizations/{id}/members` and
    `PATCH /organizations/{id}/members/{memberId}` (owner-only role changes, with
   an `organization_member.updated` audit row). There are no member removal
   routes, and the "at least one organization owner" invariant is only
   incidentally preserved by that route's self-role-change guard.
3. **Zod schemas leak server-managed fields.** `insertOrganizationInvitationSchema` is not narrowed
   (exposes `id`, `invitedBy`, `status`, `acceptedAt`, `createdAt`); the member insert schemas still
   expose `addedBy`. Narrow at the route layer; always set `invitedBy`/`addedBy` from the session.
4. **Duplicate `roleEnum` export.** Both `organizationMembers.ts` and `workspaceMembers.ts` export
   `roleEnum`; rename to `organizationRoleEnum` / `workspaceRoleEnum` before any barrel re-export.
5. **Misspelled `upadteWorkspaceMemberSchema`.** Rename to `updateWorkspaceMemberSchema`.
6. **Missing indexes.** Add `organization_members (user_id)` (only covered as the second unique-
   index column today), `organization_invitations (invited_user_email, status)`,
   `organization_invitations (invited_by)`, `workspaces (organization_id)`,
   `workspace_members (workspace_id)`, `workspace_members (organization_id)`.
7. **No domain relations.** Domain schemas have no `relations()`; keep explicit joins, or add
   relations before relying on `db.query.*`.
8. **Orphan risk on ownership.** Deleting the last owner leaves the organization unadministrable.
   Enforce "at least one owner" in the service layer or transfer ownership explicitly on removal.
9. **Tenant middlewares not consumed yet.** `organizationMemberMiddleware` /
   `workspaceRoleMiddleware` are wired but no route requires them; routes currently authorize in
   handlers. Wire future workspace-scoped mounts after those `use(...)` lines.
10. **Operational data is not attached yet.** No table references `workspace_id` (except
    `activity_logs`). Catalog/floor/orders/etc. should carry a `workspace_id` FK, and every query
    must be scoped by an authorized workspace.
